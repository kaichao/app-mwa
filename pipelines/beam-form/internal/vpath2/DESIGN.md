# vpath 定义、设计模型与重构对比

## 一、定义

**vpath（virtual path，虚拟路径）** 是共享存储的虚拟化层，也是**读写路径优化的重要概念**——它实现多读写路径的抽象管理。

它把物理上分散的多个存储空间（共享盘、远程存储）组织成若干**逻辑存储类别**，对上层只暴露一个路径查询接口。调用方按类别请求路径，不必关心数据实际落在哪个空间、存了几份、读请求如何分摊——由 vpath 依据容量、加权与副本策略决定。

计算节点本地存储不在此列——本地存储需显式表示以优化，不宜由 vpath 管理。

写入侧的分配状态通过**信号量**（各空间剩余量）与**共享变量**（数据单元 → 所在空间）维护在数据库中，因此多个进程、多个应用可以共享同一批存储资源而不互相冲突；读取侧的副本选择由 key 哈希直接得出，不产生任何状态。

由此得到的中间抽象层，是**优化数据加载的基础**：

- 写入时，把零散的小空间聚合成大空间，或把多个大空间合并成更大容量
- 读取时，把并发读请求按各空间的 I/O 能力分摊，或以多副本换取读取带宽

在 scalebox 中，vpath 承担**路径标识**职责——回答数据"在哪里"。与之并列的是 scalebox 天然支持的**异步流式传输**——回答数据"怎么搬过去"。二者是正交的两项能力，前者瞬时无副作用，后者耗时且有副作用（见第七节）。

**职责边界**：vpath 只负责标识数据单元的位置，**不负责搬运数据**——写多份、实际拷贝、部分失败的清理，都由调用方与传输模块完成。

## 二、三类存储虚拟化

### 类型 a：聚合 —— 小空间合成大空间

若干个小容量空间聚合成一个逻辑大空间，整体对外表现为容量之和。

```
小空间 A (480GB) ┐
小空间 B (480GB) ├─→  逻辑空间 (Σ 容量)
小空间 C (480GB) ┘
```

- **选择时机**：写（分配一个新数据单元的位置）
- **选择依据**：剩余量最大 —— 每次消耗当前剩余最多的成员，各成员剩余量趋于一致，最后同时用尽；不会出现"大的用完了、小的还剩一点却放不下"的情况
- **状态**：信号量记录每个空间的剩余量；共享变量记录每个数据单元落在哪个空间
- **申请**时信号量减少，**释放**时信号量增加
- **类比**：JBOD / LVM —— 把多个独立卷合成一个可用卷

#### 算法来源：严格移植现有实现，不另造轮子

类型 a 的分配算法逐行沿用 `internal/vpath/aggregator_scalebox.go` 的 `ScaleboxAggregator.Allocate`。该实现已处理「选择」与「记录」之间的一致性，重构时**逐行对照**即可核查，不要重新设计：

```
1. 查共享变量 vpath:member-path:<pool>:<key>
     命中且非空 → 直接返回（幂等：同一 key 重复调用返回同一位置）
2. 未命中 → semagroup.GetMax("vpath:free-gb:<pool>")
     取剩余量最大的成员
3. 剩余量 < need_gb → 报「空间不足」，拒绝分配
4. semaphore.AddValue(成员信号量, -need_gb)      扣减
5. variable.Set(成员变量, 成员路径)               记录
```

`Release` 与之对称：删目录 → 归还信号量 → 变量置空。

**解析成员的注意事项**：信号量名形如 `vpath:free-gb:<pool>:<member>`，而 `<member>` 自身可能含冒号（如 `astro@10.100.1.30:10022/...`）。必须用 `SplitN(name, ":", 4)[3]` 取成员路径，**不能用 `Split`**——现有 vpath 正是在 `Split(":")[2]` 处踩了这个坑（见四.C）。

### 类型 b1：复制 —— 多空间存相同数据

多个较大容量的存储空间各存一份相同数据，形成一个副本组。

```
空间 A ──┐
空间 B ──┼─→  同一份数据（3 份副本）
空间 C ──┘
```

- **选择时机**：**读**（每次读取都选一次）
- **写入**：写多份相同数据。vpath 返回副本组的全部路径，由调用方完成拷贝
- **读取**：按加权选一个空间 —— 数据处处都在，选哪个都读得到
- **加权值**：客户端选择访问哪个空间的依据，反映各空间的 I/O 能力（静态配置值，非剩余量）
- **分摊对象**：**不同 key 的分布**——key₁ 去副本 A、key₂ 去副本 B；同一 key 恒指向同一副本。从整体统计看，读量按权重分布到各副本上即可，不追求"同一份数据的多次读取也分散开"
- **容量**：不做容量检查。成员是大容量空间且数量少，由人工保证空间充足，不足时报错
- **类比**：RAID1。**写放大 N 倍**换取读带宽

### 类型 b2：合并 —— 大空间容量相加

多个大容量空间合并使用，提供容量总和。

- **选择时机**：写（分配一个新数据单元的位置），**且只在首次**——之后同 key 直接返回共享变量记录的位置
- **选择依据**：**配置中的固定权值**，不看剩余容量、不记录分配次数
- **状态**：共享变量记录数据单元落在哪个空间。b2 **不记账、不关注已用量、也不计分配次数**
- **容量耗尽**：**报错**，不跳过、不回退。成员大小不一时小空间可能先满，由人工保证容量充足
- **类比**：RAID0
- 与类型 a 的区别：**动态 vs 静态**——类型 a 按剩余量（动态）选，b2 按配置权重（静态）选；类型 a 记账，b2 不记账

#### 分配实现：加权哈希，无需计数

每个 key 只分配一次，位置固化在共享变量中，因此分配次数对**已分配的 key 毫无作用**。让新 key 的分布符合权重，用 rendezvous hashing 即可：

```
member = argmax_i ( -weight_i / ln(hash(key, i)) )
```

| 性质 | 说明 |
|---|---|
| 无状态 | 无需信号量，无读-改-写 |
| 确定性 | 同一 key 恒选同一 member，可重放 |
| 分布 | key 数量大时 ∝ 权重 |
| 权重变更 | 只影响此后新分配的 key，已分配的不动 |

前提：key 数量足够多。MWA 每次观测几百到几千个 cube，满足。

### 三类对照

| | a 聚合 | b1 复制 | b2 合并 |
|---|---|---|---|
| 类比 | JBOD / LVM | RAID1 | RAID0 |
| 成员规模 | 小容量 | 大容量 | 大容量 |
| 数据份数 | 1 | N | 1 |
| **选择时机** | **写**（每次） | **读**（每次） | **写**（仅首次） |
| 选择依据 | 剩余量最大 | 配置权重（I/O 能力） | 配置权重（固定比例） |
| 依据性质 | **动态**（剩余量） | **静态**（配置值） | **静态**（配置值） |
| 分配次数 | 每次分配 | 每次读取 | 每个 key 仅一次 |
| 容量账本 | **维护** | 不承担 | 不承担 |
| 位置记录 | 需要 | **不需要** | 需要 |
| 对外容量 | Σ 成员 | 单空间容量 | Σ 成员 |
| 写放大 | 1× | N× | 1× |

**b1 与 b2 的核心取舍**：一个用空间换管理，一个用管理换空间。

| | b1 复制 | b2 合并 |
|---|---|---|
| 空间成本 | **费**（N 份） | **省**（1 份） |
| 状态 | **无** | 有（位置记录） |
| 读 | 任选一个副本直接读 | 先查共享变量 |
| 管理成本 | **低** | 需要维护变量一致性 |

### 类型组合

**b1 与 b2 之间不叠加**——不需要"先镜像再条带"（RAID10 式）的组合。

**但类型 a 的输出可以作为组合层的成员。** 两类角色因此是分层的：

```
构建层   类型 a  ──  小空间 → 大空间     把零散的物理空间变成"一个"可用空间
组合层   类型 b1 ──  多个大空间互为副本
         类型 b2 ──  多个大空间容量相加
```

典型场景是跨站点：

```
站点 A：cstu0001..0032 的 500GB  →  聚合空间 PA
站点 B：cstu0101..0132 的 500GB  →  聚合空间 PB

b1：PA 与 PB 互为副本（异地容灾 + 分摊读带宽）
b2：PA 与 PB 容量相加（Σ）
```

**配置表达**：类型 a 的池直接作为组合层的成员列出：

```yaml
pools:
  site-a:                       # 类型 a：聚合站点 A 的 32 个小空间
    strategy: max-free
    # members 已在信号量组 vpath:free-gb:site-a 中（由 sema 文件创建）

  site-b:
    strategy: max-free

classes:
  cross-site:                   # 只描述"用哪两个站点"，不表达 b1 还是 b2
    unit_size_gb: 11
    targets:
      - pool: site-a
        weight: 1
      - pool: site-b
        weight: 1
```

注意这份配置**看不出**是 b1 还是 b2——这正是"类型由调用方选择的 API 决定，配置层不表达"的体现：

- 调 `Allocate` → b2：按权重选一个池写一份
- 调 `GetAllPaths` → b1：两个池各写一份，读时按权重选

跨站点场景两种都可能要，所以配置不该替调用方决定。

这带来**两级分配**：先在组合层选出目标池，再在池内选出物理成员。

**嵌套深度上限：2 层** —— 类型 a 位于构建层，b1 / b2 位于组合层。类型 a 可以嵌入 b1 或 b2，但不允许更深（不存在"b1 套 b2 再套 a"这样的形态）。

**容量管理只在类型 a**

| 层 | 容量账本 | 说明 |
|---|---|---|
| 类型 a | **维护** | 信号量记剩余量 + 共享变量记位置 |
| 类型 b1 | 不承担 | 组合层，只负责写多份与读时选择 |
| 类型 b2 | 不承担 | 组合层；按配置权值选空间，**选择时不读容量信息** |

即：**账本只存在于最底层的物理空间**。组合层不记账，选择时也不看容量；它选中的类型 a 空间**内部照常扣减信号量**，两层职责分明。

**成员的权威来源是信号量**

无论成员是物理路径还是另一个池，**运行时一律从信号量组读取**：

- 类型 a 的池：成员为物理空间，信号量值为剩余量，分配时扣减
- 导入方式：由 sema 文件创建（如 `preload` 池的 64 个账号空间），或在 YAML 中列出后**在加载时同步写入**信号量组

**两条已定规则**：

- **b2 不关心容量**——按配置权值算比例（见二.类型 b2），**选择时**不读成员的剩余量
- **`GetAllPaths` 逐个处理组成元素**——`path` 直接返回、`pool` 在池内各分配一块，共 n 个

## 三、模型

### 骨架：选择时机决定状态需求

三类之间的根本分界不在「聚合还是合并」，而在**选择发生在读还是写**：

| 选择的时机 | 含义 | 状态需求 |
|---|---|---|
| **读** | 数据处处都在，选错不影响正确性，最坏是负载不均 | **完全无状态**——哈希即得，不记账 |
| **写** | 数据只落在一处，选错就读不回来 | **必须有状态**——位置记录；类型 a 另需容量账本 |

类型 b1 是唯一「读时选择」的，也是唯一不需要位置记录的。

### 账本

| 类别 | 账本 | 载体 |
|---|---|---|
| 类型 a | 每个空间的剩余量 | 信号量 `vpath:free-gb:<pool>:<member>` |
| 类型 a、b2 | 数据单元 → 空间 | 共享变量 `vpath:member-path:<pool>:<key>` |
| 类型 b1 | **无** | 读位置由 key 哈希直接算出，无需记录 |

两点注意：

- 容量账本只有类型 a 维护；b2 有位置记录但**不记账**
- **类型 b1 完全无状态**——不记账、不计数、不写变量，这是无状态哈希的直接结果

#### 类型 b1 的读分摊：无状态哈希

```
replica = argmax_i ( -weight_i / ln(hash(key, i)) )
```

| 性质 | 说明 |
|---|---|
| 无状态 | 无需信号量，无读-改-写 |
| 确定性 | 同一 key 恒选同一副本，可重放 |
| 分布 | key 数量大时 ∝ 权重 |
| 多进程 | 天然一致 |

选哈希而非计数器：**无状态更易管理**。计数器要维护一套 `vpath:read-count:` 信号量、批量读回、应用侧算比值、再写回；哈希只是一个纯函数。代价是比例由精确变为统计趋近，key 数量大时（每次观测几百到几千个 cube）足够接近。

于是 b1 与 b2 共用同一段加权选择实现，读侧整条路径不产生任何状态。

> 本节能力**暂缓实现**——当前 `origin-tar` 在代码中零引用，无调用方在等它。设计保留，实现排在修 bug 之后。

### API

原来的 `GetPath` 拆成两个动词——**`Locate` 只查不写，`Allocate` 确定位置（必要时新建）**：

| 操作 | a 聚合 | b1 复制 | b2 合并 |
|---|---|---|---|
| `Locate(class, key)` | 查共享变量，**未命中返回空** | 按权重选一个副本返回（无状态哈希） | 查共享变量，**未命中返回空** |
| `Allocate(class, key)` | 命中即返回；否则选剩余量最大的成员，扣减并记录 | — | 命中即返回；否则按权重哈希选空间并记录 |
| `GetAllPaths(class, key)` | — | **返回全部 n 个副本路径**（写多份） | — |
| `ReleasePath(class, key)` | 释放 + 归还容量 | **逐成员释放，仅成员为类型 a 时有效** | 清除位置记录（不涉及账本） |
| 容量查询 | Σ 剩余 | 任一副本的容量 | Σ 成员（读成员信号量求和） |

三条约定：

- **`Locate` / `Allocate` 分离**解决了一个实际隐患：现有 `pull_unpack.go:122` 用 `GetPath` 去查源文件在哪，若变量尚未写入会**凭空分配一块空间并扣容量**。现在查就是查，未命中返回空
- **`GetAllPaths` 仅对 b1 有效**。按组成元素逐个处理：`path` 直接返回，`pool` 在池内各分配一块，共 n 个
- **类型由调用方选择的 API 决定，配置层不表达**。同一份 `targets`，调 `GetAllPaths` 即 b1（写多份），调 `Allocate` 即 b2（写一份）。**风险**：对 b2 类误用 `GetAllPaths` 会造成 N 倍容量分配

### 配置形态

配置分两层，每层只回答一个问题：

| 层 | 回答 | 内容 |
|---|---|---|
| `pools` | **空间如何组织** | 物理存储怎么组合、分配时怎么选成员 |
| `classes` | **数据放在哪** | 一类数据的大小、可选的存放位置 |

**类型不在配置里声明**：`path` 即已有位置、`pool` 即池内分配，两者如何组合决定行为；b1 与 b2 的区分由调用方选择的 API 决定（见三.API）。

类型 a 与 b2 的差异不在配置结构，而在**选择依据的动态与静态**——类型 a 看池内剩余量（动态），b2 看 `targets` 的配置权重（静态）。

```yaml
# ── 空间层：物理存储如何组织 ─────────────────────────────
pools:
  small:                        # 一批小空间，聚合成一个大空间（类型 a）
    strategy: max-free          # 分配时选剩余量最大的成员
    # members 从信号量组 vpath:free-gb:small 派生，无需在 YAML 重复

# ── 类别层：一类数据放在哪 ───────────────────────────────
classes:
  preload-tar:                  # 预加载的 tar 包
    unit_size_gb: 11            # 每份 11GB
    targets:
      - pool: small             # 写：从 small 空间分配一块

  origin-tar:                   # 原始数据，多个空间各存一份（类型 b1）
    targets:
      - path: "astro@10.100.1.30:10022/data1/mydata"
        weight: 1               # 读请求按 I/O 能力分摊；data2 是它的 3 倍
      - path: "astro@10.100.1.30:10022/data2/mydata"
        weight: 3

  cross-site:                   # 两个站点容量相加（类型 b2）
    unit_size_gb: 11
    targets:
      - pool: site-a
        weight: 1
      - pool: site-b
        weight: 1

  staging-24ch:                 # 混合：既有已存在的副本，也可分配新空间
    unit_size_gb: 29
    targets:
      - path: "astro@10.100.1.30:10022/data2/mydata"
        weight: 1
      - pool: small
        weight: 1
```

**池级的策略只有 `max-free` 一种**（类型 a 用）。类型 b2 的"固定比例"不落在池上，而落在 **`targets` 的权重**上——与 b1 用的是同一套权重机制。

**`weight` 的语义**：该 target 被选中的**相对频次**。它的作用点随类型而变：

| 类型 | weight 决定 |
|---|---|
| b1 | 读请求分到哪个副本 |
| b2 | 新数据单元写进哪个空间 |
| 混合 | 走已有副本，还是分配新空间 |

> 现有 `app/vpath.yaml` 里这个字段实际被当成开关用——`preload-tar` 把三个静态路径全设 `weight: 0.0`、`AGG_PATH` 设 `1.0`，`staging-24ch` 反过来。这说明字段语义在实践中已经模糊。重构后应显式修正：**要排除某个目标就整条注释掉，不要留一条权重为 0 的记录**——后者会让读者误判为"仍在使用"。

## 四、三版实现对比

### A. 定位与配置

| 维度 | vpath（现状） | vpath2（现状） | 重构目标 |
|---|---|---|---|
| 定位 | beam-form 应用内专用 | 应用内重构初步版，计划上提平台 | 平台通用组件 |
| 配置结构 | 扁平 `map[category]` | `{classes, pools}` 两层 | 沿用 vpath2 |
| 写目标表示 | `path: AGG_PATH` 字符串哨兵 | `target.pool:` 字段 | 沿用 vpath2 |
| 单位容量位置 | `need_gb` 挂在 AGG_PATH 上 | `unit_size_gb` 提到 class 级 | 沿用 vpath2 |
| 类型 b2 支持 | 无 | `weighted` 池策略（按 used/capacity） | 移到 **target 层**：按配置权重哈希选空间，取消池级策略 |
| 类型 b1 支持 | 只有读侧加权，**无写多份能力** | 同 | 补 `GetAllPaths` |
| 读写混合表达 | `weight: 0/1` 当开关用 | 仍靠 weight，但语义清晰 | 统一加权，混合自然表达 |
| 成员列表 | 不在 YAML，来自信号量组 | 必须在 YAML 的 `pool.members` 列出 | 回到信号量组派生 |

### B. 读侧（类型 b1）

| 维度 | vpath | vpath2 | 重构目标 |
|---|---|---|---|
| 选择算法 | `min(actual/theory)`，有状态计数 | 同 | **无状态哈希** |
| 状态 | **进程内** `counts/total` | 同 | **无** |
| 多进程一致性 | 各进程独立计数，偏差叠加 | 同 | 天然一致 |

## 五、重构要点

按优先级：

1. `strategy.go:91` 改用 `internal/varerr.IsNotFound`
2. `GetPath` 拆为 `Locate`（只查，未命中返回空）+ `Allocate`（确定位置，必要时新建）
3. **target 层的加权选择改用无状态哈希**（rendezvous hashing）。这是三类共用的机制——`path` 与 `pool` 在 `targets` 层一律按权重哈希选定，选中 `pool` 后再进池内分配。类型 b1 的读分摊与 b2 的写分摊是同一段实现
4. `ReleasePath` 按实际分配池释放，不再 `return` 第一个；b1 的 `ReleasePath` 逐成员释放，**仅对成员为类型 a 时有效**
5. 池成员从信号量组 `vpath:free-gb:<pool>` 派生，YAML 不再列 `members`
6. 补 `GetAllPaths`（类型 b1 的写多份，仅此一类有效）
7. 组合层（b1 / b2）的成员引用类型 a 的池，**最多 2 层**、不做更深嵌套；成员一律以信号量组为准，YAML 中定义的成员在加载时同步写入
8. 给 `Pool` 加注入点，让池逻辑能脱离 scalebox 测试；补 `Pool.Validate` 做配置与信号量一致性校验
9. **删除 `weightedSelector`**（有状态加权选择器），代之以无状态哈希函数。`counts/total` 状态、`selectTarget(targets)` 传错切片的隐患、多进程计数不共享的问题一并消失
10. 去掉池级 `weighted` 策略（按 used/capacity 选成员）——已由 target 层加权哈希取代

## 七、与多级加载的关系

### 7.1 两项正交能力

scalebox 提供两项正交能力，各自解决一个问题：

| 能力 | 回答 | 性质 | 现状 |
|---|---|---|---|
| vpath | 数据**在哪里** | 瞬时、无副作用、可重复调用 | 已抽象（本文档） |
| 异步流式传输 | 数据**怎么搬过去** | 有副作用、耗时、异步 | scalebox 天然支持，已有实现的模块 |

本仓库的 `tar-load` 与 `pull-unpack` 就是后者的应用实例，前者为它们提供位置标识。

### 7.2 现状：三级链已经在运行

```
远端存储                局域网共享存储              计算节点本地
astro@10.100.1.30:10022  /public/home/cstuXXXX/      /tmp/scalebox-0/
  /data2/mydata/mwa        scalebox/mydata/mwa         mydata/mwa
       │                        │                          │
       └── tar-load ────────────┘                          │
           （远端 → 共享）                                  │
                                └── pull-unpack ───────────┘
                                    （共享 → 本地）
```

| 环节 | 源 | 目标 | 位置由谁决定 |
|---|---|---|---|
| tar-load | `ORIGIN_ROOT`（远端 HPC） | `vPath.GetPath("preload-tar", key)`（`tar_load.go:96`） | **vpath** |
| pull-unpack | `vPath.GetPath("preload-tar", key)`（`pull_unpack.go:122`） | `LOCAL_TMPDIR`（环境变量） | 环境变量 |

**关键观察**：tar-load 分配位置、pull-unpack 用同一个 key 查回同一个位置——**vpath 已经在承担跨模块的位置协商**。缺的不是机制，而是"这一层的上游是谁"没有被显式表达，目前藏在 `ORIGIN_ROOT` 环境变量里。

### 7.3 与类型 b1（复制类）的区别

表面看都是"同一份数据在多处"，本质不同：

| | 类型 b1 复制 | 三级加载链 |
|---|---|---|
| 各层关系 | **平等**（同级副本） | **层级**（本地 ⊂ 共享 ⊂ 远端） |
| 读的行为 | 选一个读，其余不动 | 命中即止；未命中则**回源拉取** |
| 访问方式 | 同构（都是路径） | **异构**（ssh/scp vs POSIX） |
| 数据搬动 | 无 | **有**（分钟级、有副作用） |
| 状态语义 | **无状态**（不记账、不写变量） | **存在性 + 新鲜度**（在不在、旧不旧） |
| 容量压力 | 静态配置 | 本地盘小，需**淘汰** |

核心差异在后三行：b1 是"选一个地方读"，三级加载是"逐级回填"。前者是**选择问题**，后者是**缓存问题**。

**结论：它不是 b1 的变体，是另一种东西。**

### 7.4 边界

| 归属 | 职责 | 理由 |
|---|---|---|
| vpath | 数据单元 → 位置（哪一级、哪个空间），以及层级间的**回源关系** | 路径标识，瞬时无副作用 |
| 传输模块 | 按位置执行实际搬运 | 有副作用、耗时、异步，且需要独立资源池（`tar-load` 的 `slots: n0:3` 即是证据） |
| **不纳入** | 计算节点**本地存储** | 本地存储需显式表示以优化，不宜由 vpath 管理 |

即便要"透明"到调用方只调一个取数 API，也不应把传输塞进 `Locate` / `Allocate`——那会让一个瞬时查询变成可能阻塞分钟级的操作，vpath 也就从"路径标识"变成了"分布式缓存管理器"，名实不符。若确需统一入口，应在 vpath **之上**再建一层编排者。

### 7.5 开放问题：应用级语义能否收敛

真正的瓶颈不在传输能力（scalebox 已有），而在于**把多级加载抽象为统一范式，传输环节需要注入远多于路径标识的应用级语义**。这些语义能否被配置表达、能表达多少，尚未检验。

`tar-load` 与 `pull-unpack` 目前承载的语义，按通用性分类：

| 语义 | 内容 | 通用性 |
|---|---|---|
| 数据切分 | 按 obsID / 时间范围 / 通道数决定加载哪些文件 | **应用特有** |
| 文件命名 | `%d_%d_ch%d.dat.tar.zst` | **应用特有** |
| 通道分组 | `pod_id: by_channel`、`key_group_regex` | **应用特有** |
| 加载顺序 | 按 time-range 顺序 | 半通用（排序键可由配置给出） |
| 目标位置 | vpath 类别 | 通用 |
| 源位置 | 上游地址 | 通用 |
| 并发度 | `slots` | 通用（平台已支持） |
| 限速 | `FIRST_BW_LIMIT` / `BW_LIMIT` | 通用 |
| 源保留 | `KEEP_SOURCE` | 通用 |
| 完成通知 | `tar-ready` / `dat-ready` 信号量 | 通用（信号量机制） |
| 冲突处理 | `CONFLICT_ACTION=OVERWRITE` | 通用 |

**观察**：通用部分占多数，应用特有的部分集中在**"数据单元如何切分与命名"**。这提示了一条可能的抽象路径——把应用特有的部分收敛为配置中的「数据单元标识规则 + 命名规则」，其余全部通用化。

**但这只是单一天文场景的观察。** 能否覆盖异构应用，判据是：

1. 数据单元的切分规则能否用配置表达（而非每种应用写一段代码）
2. 回源触发条件能否收敛（现在是"一开始就全量预加载"，而非"用到才拉"）
3. 淘汰策略是否需要（本地盘会满——现在靠 `slot_timeout_minutes` 和外部清理）
4. 限速、重试、断点续传等传输语义是否已在 scalebox 侧足够通用

这四条验证通过之前，**多级加载宜保持"vpath 提供位置 + 传输模块独立实现"的形态**，不急于抽象为统一范式。
